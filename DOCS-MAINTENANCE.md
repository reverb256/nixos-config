# Documentation Maintenance Policy

> **Status:** Canonical policy
> **Last Verified:** 2026-08-09
> **Owner:** j_kro
> **Scope:** Markdown and operational documentation in this repository

This policy defines how documentation is classified, verified, maintained, and retired.
It does not make a historical document current merely by changing its timestamp.

## Authority boundaries

- [`docs/current-state.md`](docs/current-state.md) is the concise checked-in architecture
  and documentation-routing reference.
- [`AGENTS.md`](AGENTS.md) is the canonical operational safety and agent policy.
- [`CONTRIBUTING.md`](CONTRIBUTING.md) is the canonical contribution/worktree workflow.
- [`DOCUMENTATION_INDEX.md`](DOCUMENTATION_INDEX.md) is the repository-wide catalog.
- `STATUS.md` is a generated snapshot and must be treated as stale when its underlying
  snapshot or generator run is stale.
- `ROADMAP.md` is roadmap/migration history and hardening context, not a live health
  dashboard.
- Dated audits, incident reports, and archived plans are historical evidence. Re-verify
  their commands and claims before using them operationally.

For live claims, use `just health`, `just status`, `just provenance`, Kubernetes queries,
and host/service checks. Prose is not a substitute for runtime evidence.

## Documentation classes and required metadata

Every maintained document must have a visible classification. Use the metadata style
already used by the surrounding document; YAML frontmatter is recommended for new
standalone documents but is not yet required across the legacy tree.

| Class | Required metadata | Operational rule |
|---|---|---|
| Canonical | `Status`, `Last Verified`, `Owner` | Keep links and workflow claims current |
| Active | `Status`, `Last Verified`, `Owner` or `Source` | Commands must be checked against source/config |
| Reference | `Status`, `Last Verified`, `Owner` or `Source` | Avoid unqualified live-state claims |
| Generated | `Status`, `Generated By`, `Source of Truth` | Do not hand-edit generated sections |
| Historical | `Status: Historical`, original date, `Source` | Preserve timeline; do not follow blindly |
| Archived/Deprecated | `Status: Archived` or `Deprecated`, reason/date | Put a warning before operational commands |
| Template | `Status: Template`, `Owner` | Keep placeholders obvious and safe |

The existing repository contains legacy documents without this metadata. The enforced
active set is declared in `docs/meta/VERIFICATION-SUITE/ACTIVE-DOCUMENTS.txt` and checked
by `verify-staleness.sh`; other legacy reference documents remain discoverable but are not
eligible as current procedures until individually verified. Do not add fabricated verification dates to unreviewed files.

## Freshness rule

For active operational documentation, `Last Verified` means the content was checked
against the current repository and, where it makes runtime claims, the live host/cluster.
A file's Git modification date is not a verification date.

- Active operational docs older than 7 days require re-verification before use; the suite defaults to this 7-day threshold.
- A document outside the enforced active set must be treated as legacy/reference until
  it receives individual source and command verification.
- Canonical policy/navigation docs should be reviewed whenever their referenced paths or
  workflows change.
- Historical documents retain their original dates; they do not need artificial refreshes.
- Generated snapshots must expose both generation time and source-of-truth snapshot time.

Use this banner when a document is known to be stale but must remain discoverable:

```markdown
> **Status:** Historical / Archived
> **Last Verified:** YYYY-MM-DD (historical verification date)
> **Do not follow operational commands without re-validating them against the current repository.**
```

## Safe documentation workflow

1. Identify the document class before editing.
2. Check the canonical source/configuration path named by the document.
3. Check for duplicate or superseding documents in `DOCUMENTATION_INDEX.md` and the
   cleanup manifest.
4. Update the document's status/verification metadata when the content is verified.
5. Update inbound links and the relevant index in the same change.
6. Run the documentation verification suite.
7. Review the diff for accidental changes to Nix, shell, YAML, workflows, or secrets.

Do not silently rewrite incident timelines. Do not copy plaintext secrets into examples,
logs, screenshots, or documentation.

## Current tooling status

The documentation checks now share the same authority model:

- `docs/meta/VERIFICATION-SUITE/run.sh` runs active metadata, source-of-truth, and
  repository-relative cross-reference checks.
- `just docs-audit` invokes the verification suite.
- `.claude/hooks/validate-docs.sh` delegates to the same repository-relative suite.
- CI documentation jobs fail when the suite fails; they do not downgrade rot to a warning.
- `scripts/update-status.sh` generates root `STATUS.md` from `cluster-state.nix` plus live
  Kubernetes queries when available.

The suite intentionally checks the explicit active-document set and excludes historical
archive material from freshness checks. A passing suite validates the maintained set, not
every historical document in the repository.

## Repository structure policy

- Root canonical docs remain discoverable from `README.md` and `DOCUMENTATION_INDEX.md`.
- Active operational runbooks belong under `docs/runbooks/` or an explicitly documented
  subsystem directory.
- `docs/LIVE/` is a compatibility-pointer directory, not a source of truth; do not add
  new current-state documents there.
- Active plans belong under `docs/plans/` and require `Last Verified` metadata.
- Historical audits, incidents, completed plans, and research belong under the lowercase
  `docs/archive/` tree. The former uppercase archive is preserved intact under
  `docs/archive/legacy/ARCHIVE/` for path/history compatibility.
- Subsystem READMEs must identify their source of truth: Nix/Easykubenix, raw YAML,
  Helm/operator, bootstrap-only, test-only, or archived reference.
- Generated status files must name their generator and source-of-truth file.

## Validation commands

```bash
# Repository-level documentation checks
just docs-audit

# Direct verification suite
./docs/meta/VERIFICATION-SUITE/run.sh

# Navigation and basic diff checks
 git diff --check
 git status --short
```

For a documentation-only change, verify that the diff does not include unrelated `.nix`,
`.sh`, `.yaml`, workflow, or secret changes. Preserve pre-existing working-tree changes
and review them separately.
