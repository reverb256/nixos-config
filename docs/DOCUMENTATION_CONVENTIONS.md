# Documentation Conventions

**Version:** 1.0
**Created:** 2026-03-21
**Status:** ✅ Active

---

## Core Principles

1. **Single Source of Truth** - One canonical document per topic
2. **Progressive Disclosure** - Overview → detailed → reference
3. **Git for Versioning** - Use git history, not filename versions
4. **Time-Based Archive** - Incident reports in dated folders

---

## File Naming Conventions

### ✅ DO: Use Descriptive Names

```
✅ akash-provider-status.md          # Always current
✅ searxng-troubleshooting.md        # Topic-specific
✅ gpu-passthrough-setup.md          # How-to guide
✅ CLAUDE.md                          # Reference documentation
```

### ❌ DON'T: Date-Stamp Reference Docs

```
❌ akash-provider-status-2026-03-21.md
❌ searxng-fix-2026-03-21.md
❌ gpu-passthrough-2026-03-21.md
```

**Why:** Date-stamped filenames create version confusion. Use git history for past versions.

---

## Exception: Incident Reports

Incident reports SHOULD be date-stamped and archived:

```
docs/incidents/2026-03-21/
├── searxng-http-403-errors.md
├── kubernetes-ip-exhaustion.md
└── gpu-mining-crashloop.md
```

**Rationale:** Incidents are time-bound records. Archive by date for historical analysis.

## Document Types

### 1. Reference Documentation (No Dates)

**Location:** `/etc/nixos/docs/` or root `/etc/nixos/*.md`

**Purpose:** Living documentation, always current

**Examples:**
- `CLAUDE.md` - Agent workflows
- `AGENTS.md` - MCP integration
- `ROADMAP.md` - Migration plan
- `STATUS.md` - Cluster status (auto-generated)

**Updating:** Edit in-place, commit changes with descriptive messages

**Versioning:** Use git history for past versions

---

### 2. Incident Reports (Dated)

**Location:** `/etc/nixos/docs/incidents/YYYY-MM-DD/`

**Purpose:** Time-bound records of disruptions and investigations

**Examples:**
- `docs/incidents/2026-03-21/searxng-http-403-errors.md`
- `docs/incidents/2026-03-19/gpu-mining-crashloop.md`

**Updating:** Create new file for each incident

**Archiving:** Keep in dated folder, never move or rename

**Template:** Use `docs/incidents/INCIDENT_TEMPLATE.md`

---

### 3. Status Documents (Manual vs Auto)

**Manual Status:**
- **Updated:** When cluster state changes significantly
- **Frequency:** Weekly or after major changes
- **Example:** `ROADMAP.md` phase completion status

**Auto-Generated Status:**
- **Updated:** By script on schedule
- **Frequency:** Hourly or daily
- **Example:** `STATUS.md` (regenerated by `scripts/update-status.sh`)

**Rule:** If it's auto-generated, say so in the header.

## Document Structure

### Reference Docs

```markdown
# Title

**Purpose:** [What this doc covers]
**Audience:** [Who should read this]
**Last Updated:** YYYY-MM-DD
**Status:** ✅ Current / ⚠️ Needs Update / ❌ Deprecated

## Overview
[High-level summary]

## Configuration
[How it works]

## Troubleshooting
[Common issues and fixes]

## References
[Related docs, external links]
```

### Incident Reports

Use the template at `docs/incidents/INCIDENT_TEMPLATE.md`

## Writing Guidelines

### Clarity

- **Be concise:** One idea per paragraph
- **Be specific:** Use exact commands, file paths, error messages
- **Be accurate:** Verify commands work before documenting
- **Be honest:** Document known issues and workarounds

### Formatting

- **Code blocks:** Use \`\`\`bash for commands, \`\`\`nix for NixOS config
- **Tables:** Use for structured data (status, comparisons)
- **Emojis:** Use sparingly for status indicators (🟢 🟡 🟠 🔴)
- **Bold:** Use for emphasis, not for entire paragraphs

### Updates

- **Timestamps:** Update "Last Updated" when content changes
- **Changelog:** Add "Recent Changes" section for major updates
- **Deprecation:** Mark obsolete docs as ❌ Deprecated, don't delete immediately

## Git Workflow

### Commit Messages

```
✅ Good: "docs(searxng): add HTTP 403 troubleshooting guide"
✅ Good: "fix(kubernetes): update GPU passthrough for RTX 4060"
❌ Bad: "update docs"
❌ Bad: "fix stuff"
```

### Branching

- **Main branch:** Always should have accurate, working documentation
- **Feature branches:** Can have WIP documentation
- **Documentation PRs:** Review for accuracy before merging

### Review Checklist

Before committing documentation changes:

- [ ] All commands tested and verified
- [ ] File paths are correct
- [ ] Links (internal and external) work
- [ ] No date-stamped filenames (except incident reports)
- [ ] Status indicators are accurate
- [ ] Known issues documented if claiming completion

## Maintenance

### Weekly

- Review STATUS.md for stale information
- Check for duplicate documentation
- Archive resolved incidents to dated folders

### Monthly

- Audit documentation for accuracy
- Remove obsolete docs (mark as deprecated first)
- Update ROADMAP.md with progress
- Review incident patterns for systemic issues

### Quarterly

- Major documentation audit (like DOCUMENTATION_AUDIT_2026-03-21.md)
- Update CLAUDE.md with new patterns
- Consolidate and refine documentation
- Update templates and conventions

## Common Mistakes

### ❌ Mistake 1: Date-Stamping Everything

```
❌ Created: gpu-setup-2026-03-21.md
❌ Created: gpu-setup-2026-03-22.md (update)
❌ Created: gpu-setup-2026-03-23.md (another update)
```

**Problem:** Which one is current? What changed between versions?

**Fix:**
```
✅ Edit: gpu-setup.md (update in place)
✅ Commit: "docs(gpu): update RTX 4060 configuration"
✅ History: Use git log to see past versions
```

---

### ❌ Mistake 2: Multiple Status Docs

```
❌ akash-provider-status.md
❌ akash-provider-status-2026-03-21.md
❌ akash-provider-update-2026-03-21.md
❌ akash-provider-summary.md
```

**Problem:** Conflicting information, unclear which is authoritative

**Fix:**
```
✅ akash-provider-status.md (single source of truth)
✅ docs/incidents/2026-03-21/akash-outage.md (incident record)
```

---

### ❌ Mistake 3: Investigation Files in Main Docs

```
❌ docs/debugging-complete-2026-03-21.md
❌ docs/akash-provider-audit-issue.md
❌ docs/ai-inference-gateway-container-issue.md
```

**Problem:** These are incident reports, not reference documentation

**Fix:**
```
✅ docs/incidents/2026-03-21/debugging-session.md
✅ docs/incidents/2026-03-21/akash-provider-audit.md
✅ docs/incidents/2026-03-21/gateway-container-issue.md
```

---

### ❌ Mistake 4: False Completion Claims

```
❌ "Status: ✅ 100% COMPLETE" (with known issues outstanding)
```

**Problem:** Misleads operators about actual state

**Fix:**
```
✅ "Status: ✅ 95% COMPLETE"
✅ "Known Issues:"
✅   - ⚠️ Issue 1
✅   - ⚠️ Issue 2
```

## Examples

### Good Documentation

**STATUS.md:**
- Auto-generated header says so
- Known issues clearly listed
- 95% complete with specific gaps documented
- Manual refresh instructions provided

**ROADMAP.md:**
- Phases marked 95% complete with outstanding issues
- Clear distinction between completed and pending
- Historical entries preserved but marked as such

**Incident Report:**
- Uses template consistently
- Timeline with exact timestamps
- Root cause analysis with five whys
- Prevention measures with owners and due dates

### Bad Documentation (Don't Do This)

**Multiple conflicting status docs:**
- `akash-status.md` says "operational"
- `akash-status-2026-03-21.md` says "broken"
- `akash-summary.md` says "partial degradation"

**Fix:** Keep one canonical status doc, archive old versions via git
